It includes the rules needed to safely expose those routes: strict money, ordered equal allocation, exact allocation, membership, transactional persistence, and concurrent group-scoped idempotency. Balances, DELETE, and frontend remain outside this request. This is a plan, not a record that checks or remote actions have passed.

## 1. POST: write the acceptance tests first

Write failing tests for new `201` and replay `200` responses, equal/exact examples, strict monetary input, zero shares, input/split validation, and descriptive errors. Cover payer different from requester, payer excluded from split, and unauthorized caller/payer/participants.

Test changed-but-valid-shaped replay, authorization before key lookup, same key in different groups, and the framework's rejection of malformed JSON/body shapes. Use real concurrent connections to verify one expense, complete unique shares, the same returned identity, and no partial writes.

Record the initial failures as evidence that the new tests exercise missing behavior rather than merely restating existing tests.

## 2. POST: implement and verify

Add an Alembic migration and matching SQLAlchemy models for immutable expense data and ordered shares. Use `NUMERIC(12,2)`, group-scoped key uniqueness covering deleted rows, and the constraints appropriate to those tables. Store a deletion flag without adding a DELETE route.

Implement request/response schemas with extra-field rejection, service validation, repository access, and the POST route. Keep strict money checks ahead of normalization/storage. Resolve existing keys after group authorization and before new-expense business validation. Insert with `ON CONFLICT DO NOTHING` and select the winning row under READ COMMITTED; expense and shares commit together.

Run POST tests, the existing suite, relevant lint/format checks, migration generation/drift checks, and concurrency tests against PostgreSQL 16. Inspect the diff and make the first coherent implementation commit only after its checks pass. Do not imply balances or soft deletion are complete.

## 3. GET: test, implement, and commit

Implement listing through repository/service/route layers, then verify GET and POST together. Inspect the change and commit the listing milestone after the relevant checks pass.
